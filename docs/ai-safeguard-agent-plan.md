# AI Safeguard Agent 구축 방안

## 1. 목적
AI Safeguard Agent는 임직원이 ChatGPT, Claude, Gemini 등 **외부 고성능 AI 서비스**를 사용할 때,
프롬프트에 포함된 민감정보를 사전에 탐지·통제하고,
사후에는 전송 이력과 이상징후를 모니터링하여
**외부 AI 활용을 허용하되 보안 통제를 단일 채널에서 수행**하는 구조를 목표로 한다.

핵심 개념은 간단하다.

- 임직원은 외부 AI를 직접 접속하지 않고
- **AI Safeguard Agent**를 통해서만 사용한다.
- Agent가 입력 내용을 먼저 점검한다.
- 민감정보가 있으면 마스킹 여부를 사용자에게 선택하게 한다.
- 이후 외부 AI로 전달한다.
- 모든 사용 내역은 내부 로그와 모니터링 시스템으로 연결한다.

---

## 2. 결론: 실현 가능성

## 결론
**실현 가능하다.**
다만 아래처럼 나눠서 봐야 한다.

### 바로 가능한 것
- 패턴 기반 민감정보 탐지
- LLM 기반 문맥 이해 민감정보 탐지
- 마스킹/원본 유지 선택 UI
- 외부 AI 단일 게이트웨이 구조
- 프롬프트/응답/사용자/시간 로그 저장
- DLP/이상징후 모니터링 연동

### 설계가 중요한 것
- "무엇을 민감정보로 볼지" 정책 정의
- 오탐/과탐 감소
- 마스킹 후 답변 품질 유지
- 사용자 예외 승인 절차
- 로그 저장 범위와 개인정보 처리 기준

### 주의할 것
- "온프레미스로 모든 처리가 이루어진다"는 표현은 정확히 나눠야 한다.
  - **탐지/마스킹/로그/정책 엔진**은 온프레미스 가능
  - **외부 AI를 쓰는 순간 추론 자체는 외부 서비스에서 처리됨**
- 따라서 정확한 구조는:
  - **사전 통제와 사후 통제는 내부(온프레미스)**
  - **최종 답변 생성은 외부 AI 서비스**

즉,
> 이 시스템은 "외부 AI를 없애는 구조"가 아니라
> "외부 AI 사용을 안전하게 중계·통제하는 구조"다.

## 4. 구축 방안

## 4-1. 민감정보 정의
민감정보는 우선 아래 5개 범주로 정의한다.

| 유형 | 예시 |
|---|---|
| 개인정보 | 성명, 연락처, 이메일, 주민등록번호, 주소, 계좌번호 |
| 기업 식별 정보 | 거래처명, 협력사명, 특정 법인명, 고객사명 |
| 사업 내용 | 신규 사업 계획, 전략, 미공개 프로젝트명, 개발 코드명 |
| 재무 정보 | 매출, 영업이익, 계약금액, 투자금액, 예산 |
| 기타 | 내부 의사결정, 미공개 일정, 계약 체결 예정 정보 |

### 추가 권장 항목
- 인사 정보: 조직/직급/평가/이동 계획
- 기술 정보: 소스코드, 아키텍처, 보안구성, API Key
- 법무 정보: 계약서 전문, 분쟁 내용, 감사 결과

## 4-2. 탐지 방식
탐지는 2단계로 가는 게 가장 현실적이다.

### 1단계: 패턴 탐지
정형 데이터는 룰로 잡는다.

예:
- 주민등록번호 패턴
- 연락처 패턴
- 이메일 패턴
- 카드/계좌/사업자번호 패턴
- 금액 표기 패턴 (예: 3,200억원)
- 날짜 패턴

장점:
- 빠름
- 설명 가능성 높음
- 온프레미스 구현 쉬움

단점:
- 형식 없는 기업정보는 잘 못 잡음

### 2단계: AI 문맥 이해 탐지
비정형 데이터는 LLM/SLM으로 분류한다.

예:
- "3,200억원 규모의 신규 공장 투자 계획"
- "A사와 2026년 3월 체결 예정"
- "B 프로젝트는 다음 분기 이사회 안건"

이런 건 패턴만으로는 부족하므로,
문장 전체를 보고 아래처럼 태깅한다.

```json
{
  "detected": true,
  "items": [
    {"type": "재무정보", "text": "3,200억원", "reason": "투자금액"},
    {"type": "사업내용", "text": "신규 공장 투자 계획", "reason": "미공개 사업계획"},
    {"type": "일정", "text": "2026년 3월", "reason": "미공개 계약 일정"}
  ]
}
```

### 추천 구조
- **패턴 탐지 먼저**
- 그 다음 **문맥 탐지**
- 마지막으로 **정책 엔진**이 중요도 판단

이 순서가 속도/비용/정확도 균형이 좋다.

---

## 4-3. 사용자 선택 방식
민감정보가 탐지되면 UI에서 아래 선택지를 준다.

### 기본 옵션
1. **전체 마스킹**
2. **원본 유지**

### 실제 운영에서는 이걸 추천
3. **항목별 선택 마스킹**

예:
- 기업명만 마스킹
- 금액만 마스킹
- 연락처만 마스킹

이게 필요한 이유는,
모든 걸 가리면 답변 품질이 떨어질 수 있기 때문이다.

### 운영 정책 추천
- 기본값은 **전체 마스킹**
- 원본 유지 시:
  - 사용자 확인 체크
  - 사유 입력
  - 로그 강화
  - 특정 등급 이상만 허용 가능

---

## 4-4. 학습/정확도 향상 구조
요청한 문구처럼,
사용자 선택 결과를 반영해 정확도를 높이는 구조는 가능하다.

다만 표현은 이렇게 바꾸는 게 정확하다.

### 권장 표현
- "자동으로 학습에 반영된다" 보다
- **"사용자 피드백이 탐지 정책 개선 데이터로 축적된다"**

이유:
- 실시간 온라인 러닝처럼 들리면 위험함
- 보안 시스템은 검증 없는 자동학습보다
  **검토 후 룰/모델 개선**이 안전함

### 현실적인 방식
- 사용자 선택 로그 저장
- 오탐/미탐 샘플 수집
- 주기적으로 검토
- 룰 업데이트 / 분류모델 재튜닝

즉,
> "사용할수록 정확도가 높아진다"는 방향은 맞지만,
> 운영상은 **자동반영**보다 **검토 후 반영**이 맞다.

## 5. 사전·사후 통제 체계

## 5-1. 사전 통제
흐름:

1. 임직원 프롬프트 입력
2. 민감정보 자동 탐지
3. 탐지 결과 UI 표시
4. 마스킹 / 원본 유지 선택
5. 정책 검사
6. 외부 AI 서비스 전송

### 차단 정책 예시
- 주민등록번호 포함 → 무조건 차단
- 계약서 원문 포함 → 마스킹 강제
- 일정 금액 이상 투자정보 포함 → 경고 + 승인 필요
- 소스코드/보안구성 포함 → 외부 AI 전송 금지

---

## 5-2. 사후 통제
전송 이후엔 아래를 기록한다.

### 저장 대상
- 사용자 ID
- 부서
- 시간
- 사용 모델
- 탐지된 민감정보 유형
- 마스킹 여부
- 원본 유지 여부
- 요청 길이 / 응답 길이
- 위험 점수

### 연동 대상
- DLP 시스템
- SIEM
- 내부 이상징후 탐지
- 보안관제 대시보드

### 이상징후 예시
- 특정 사용자가 반복적으로 원본 유지 선택
- 특정 부서에서 대량의 계약정보 전송
- 야간 시간대 대량 전송
- 같은 협력사명/프로젝트명이 반복 노출
- 갑자기 사용량 급증

## 9. 이 방안의 장점

### 1) 외부 AI를 금지하지 않고 통제할 수 있음
업무 생산성을 유지하면서 보안을 붙일 수 있다.

### 2) 단일 채널화 가능
임직원이 제각각 외부 AI를 쓰는 걸 막고,
하나의 통제된 게이트웨이로 모을 수 있다.

### 3) 점진적 확장 가능
ChatGPT만 먼저 붙이고,
이후 Claude/Gemini 등으로 확장 가능하다.

### 4) 고성능 모델 활용 가능
온프레미스 소형모델은 탐지용,
외부 고성능모델은 답변용으로 역할 분리 가능.

## 11. 추천 최종 표현

### 핵심 정의
AI Safeguard Agent는 **외부 AI 서비스 활용을 위한 단일 보안 게이트웨이**로,
프롬프트 입력 단계에서 민감정보를 탐지·통제하고,
전송 이후에는 로그 및 정보유출 모니터링 체계와 연계하여
임직원이 고성능 외부 AI를 보다 안전하게 활용할 수 있도록 지원하는 체계이다.

**높음**

**높음**
